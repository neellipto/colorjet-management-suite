# Product Master + Contact Summary Import

Source files (supplied by the business owner, not generated by this session):

- `COLORJET_MSSQL_PRODUCT_MASTER_REGENERATED_FINAL_202609066.xlsx` — 387 products,
  each assigned a brand-new canonical Product Code (old code preserved as
  `LegacyInternalReference`).
- `Contact_Summary_final_report_New.csv` — 597 party/ledger rows (Name, Address,
  Contact No, Opening/Debit/Credit/Balance).

## Two-part, audit-first process

This follows the same pattern used for Phase A (Customer 360) and Phase B
(Engineer 360): **never write to a canonical table on guessed column names.**

### Part 1 — `11_product_master_contact_import.sql` (safe to run now)

- Creates a new `stg` (staging) schema — not a canonical master, just a
  landing area for the spreadsheet data.
- Loads all 387 product rows and 597 contact rows verbatim into
  `stg.ProductMasterImport` / `stg.CategoryMasterImport` / `stg.ContactSummaryImport`.
- Runs read-only reconciliation counts against the live `dbo.Products` and
  `dbo.Accounts` tables (matches by legacy code / name / phone) so we know
  up front how many rows are genuinely new vs. already present.
- Touches **zero** rows in any `dbo.*` canonical table.

Run it, then run:

### Part 1b — `PRODUCT_IMPORT_SCHEMA_AUDIT.sql` (read-only)

Returns the full column list, keys, and foreign keys for
`dbo.Products`, `dbo.ProductCurrentStocks`, `dbo.ProductWarehouses`,
`dbo.ProductSerials`, `dbo.Accounts`, and any Category/Subcategory/Unit/Brand
tables — plus a few live sample rows so we can see real values, not just
metadata.

Paste the output back (metadata + a handful of sample rows only — no need
to share full customer data).

### Part 2 — not written yet

Once the schema audit output is in hand, Part 2 will be a `MERGE` from
`stg.ProductMasterImport` into `dbo.Products` (+ related tables) and from
`stg.ContactSummaryImport` into `dbo.Accounts`, keyed on
`LegacyInternalReference` / `Code` and `Name`/`ContactNo` respectively, so:

- a product/account that already exists is never duplicated (update only,
  or skipped, per your choice once we see the reconciliation counts),
- a genuinely new product/account is inserted once,
- the whole thing runs inside a transaction with row-count output before
  commit, exactly like `07_phaseA_customer_portal_reuse.sql` did.

Do not run any hand-written `INSERT INTO dbo.Products` against production
before Part 2 exists — that's the guess this process is specifically
avoiding.
